# 策略开发规范摘要

本文档沉淀策略从研究原型到系统落库的开发规范要点：原型三底线、落地决策树、复合体拆解、零隐藏参数与入库验收标准。开发新策略、评审研究员策略、策略系统化（onboarding）时对照执行。

## 一、策略开发两阶段生命周期

```
原型阶段（strategy-dev）      →      落库阶段（strategy-onboard）
独立脚本快速验证想法                  按规范重写为系统模块、前端配置化
```

- 原型允许粗糙，但**必须对齐目标系统的三层架构与核心签名**，保证低成本落库；
- 落库不是简单复制原型代码，而是拆解为系统模块（选择器/分配器/控制器）翻写入系统，最终通过前端界面配置实例化运行。

## 二、原型阶段三底线

1. **模块化**：signal / allocator / risk_control 分文件实现，禁止单文件大杂烩；
2. **参数集中**：所有参数统一在 config 管理，禁止散落魔法数字；
3. **数据解耦**：data_loader 是唯一 IO 入口，策略逻辑不直接读文件/数据库。

## 三、落地决策树

| 情形 | 决策 |
|---|---|
| 原型与系统现有模块**逻辑有实质差异** | 新建模块，不修改现有模块 |
| 原型是现有模块的**简单增强** | 合入原模块，且保证 `leverage=1`（或等价开关）时可完全回退到原行为 |
| 原型是**复合体**（多子策略合成） | 按复合体拆解法处理（见下节） |

## 四、复合体拆解法

**判断信号**：原型代码中先计算多个子策略的收益，再按权重线性组合（`raw_ret = w1×ret_A + w2×ret_B`）——这是收益层复合结构。

**正确做法**：拆分为
1. 子策略 A（策略模型）：独立选择器 + 分配 + 控制；
2. 子策略 B（策略模型）：同上；
3. 母组合（组合模型）：sub_strategies=[A, B] + 组合层控制。

**反模式**：把复合体注册为单一 allocation 策略——会造成目录碎片化、命名误导、无法独立复用子策略。

## 五、零隐藏参数原则

所有影响结果的参数必须：
- 显式出现在参数 Schema（`get_param_schema()`）中；
- 前端可见、可配置、可回显；
- 禁止硬编码在代码里的隐式常量（如默认窗口、阈值、延迟天数）——必须参数化或显式声明。

## 六、反模式清单

1. ❌ 单文件实现 signal+allocation+risk_control 全部逻辑；
2. ❌ 数据读取散落在策略函数内部；
3. ❌ 复合体注册为单一策略；
4. ❌ 隐藏参数（魔法数字）；
5. ❌ 修改现有模块但不保证可回退；
6. ❌ 与原型行为对齐验证缺失就入库。

## 七、策略落库四维验收标准

策略落库必须通过四个维度验收：

1. **功能正确**：回测结果与原型数值对齐（基线 NAV 对比，关键指标误差在容忍范围内）；
2. **参数完备**：Schema 完整、前端可配置可回显、默认值与原型一致；
3. **架构合规**：三层归属正确（selection/allocation/control）、注册表声明、集合名走常量；
4. **可运维**：支持监控注册、实盘发布、参数版本记录。

## 八、研究员策略特殊通道

hybrid_12、sharpe_18 等研究员策略走**数据库驱动 + 系统内运行 + 监控适配**的接入规范：
- 权重/调仓数据由研究员提供（落专用集合，如 sharpe_rebalance_weights）；
- 系统内以标准模型形态运行，接入监控与回测体系；
- 接口遵循系统规范，不引入独立运行框架。
